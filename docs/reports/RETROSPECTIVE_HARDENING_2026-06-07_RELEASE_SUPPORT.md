## Findings And Hardening

P1 - Entry docs still pointed at pre-release or pre-support proof
Evidence: roadmap and kanban proof rows still referenced earlier 2026-06-07 reports and `v0.1.2` artifact state.
Impact: future work could treat fallback zip or package settings confirmation as the next distribution task, even though `v0.1.3` installer and support settings are already implemented.
Fix: update `plan.md`, roadmap, implementation kanban, and `reports/README.md` to the accepted proof set above.
Verification: `python scripts/check_web_app.py` and `git diff --check`.

P1 - Release support guidance needed to be part of the product, not only README text
Evidence: a GitHub Release downloader may never read repository docs after installing.
Impact: users could miss unsigned-installer, no-auto-update, backup, Security, and asset-license guidance.
Fix: keep Release/support/backup guidance in Settings and assert it in Web, Electron, package, and installer smokes.
Verification: `npm run smoke:web`, `npm run smoke:electron`, `npm run smoke:package`, `npm run smoke:installer`.

P1 - External links in Electron need an allowlist
Evidence: Settings adds outbound links from a desktop shell.
Impact: a future link or injected navigation could open arbitrary URLs if Electron navigation is not constrained.
Fix: allow only `https://github.com/imonoonoko/ONOKO_ARCANA` paths through `shell.openExternal`.
Verification: `scripts/check_web_app.py` and `scripts/smoke_electron_app.cjs` check `setWindowOpenHandler`, `will-navigate`, `shell.openExternal`, host, and repo path terms.

P2 - Automated installer smoke cannot prove the full Windows install experience
Evidence: `npm run smoke:installer` launches `win-unpacked/ONOKO ARCANA.exe`, not a clean installed shortcut through Windows shell.
Impact: SmartScreen, antivirus policy, Desktop/Start Menu icon rendering, uninstall cleanup, and consumer-machine friction remain unknown.
Fix: add and use `docs/release/INSTALLER_MANUAL_SMOKE_CHECKLIST.md` before promoting the preview or changing installer/signing behavior.
Verification: run the checklist on a clean Windows user or VM and record the result in the next release checklist.

P2 - Generated evidence can become misleading if every latest run is treated as current truth
Evidence: reports are ignored by default and many timestamped runs exist locally.
Impact: future handoffs may cite stale report names or over-commit generated output.
Fix: keep only representative proof references in roadmap/kanban/reports policy; do not force-add generated reports by default.
Verification: `git status --short` should show generated reports untracked/ignored unless intentionally promoted.

## Completion Gate For Future Release Slices

Do not mark a release/support slice complete until all checks pass:

1. Official artifact check: setup.exe, fallback zip, and `.sha256` files are generated by CI or documented as local-only.
2. App guidance check: Settings shows latest Release, Security, License, unsigned/no-auto-update warning, and backup cue.
3. Link safety check: Electron external links are allowlisted.
4. Data safety check: history and learning export paths still work before update/uninstall guidance is advertised.
5. Package check: Web, Electron, local package, and installer smokes pass.
6. Manual path check: clean Windows installer checklist is run before release promotion or installer behavior changes.
7. Evidence check: `plan.md`, roadmap, implementation kanban, release checklist, residual risk register, and `reports/README.md` point to the same accepted proof set.

Run `docs/release/INSTALLER_MANUAL_SMOKE_CHECKLIST.md` on a clean Windows user or VM, then continue with history filter expansion. Keep code signing, MSIX, Store, and auto update behind a separate requirements gate until installer feedback is known.
